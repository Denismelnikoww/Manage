## 1. Назначение и общие принципы доставки уведомлений

Документ формализует события-триггеры, правила маршрутизации, точные шаблоны сообщений и политику отказоустойчивой доставки для модуля **«Telegram-уведомления» (WBS 4.5)** (покрывает [[Высокоуровневые требования#Функциональные требования|FR-06]], [[Высокоуровневые требования#Нефункциональные требования|NFR-05]], [[User Stories#US-10: Привязка Telegram-аккаунта через бота|US-10]], [[User Stories#US-11: Мгновенные Telegram-уведомления студенту|US-11]], [[User Stories#US-12: Telegram-уведомления преподавателю о новых сдачах|US-12]], [[Use Cases#UC-07: Привязка Telegram-аккаунта|UC-07]], [[Use Cases#UC-08: Доставка уведомлений через Telegram-бота|UC-08]]).

### Ключевые архитектурные требования:
1. **Асинхронность (Non-blocking HTTP):** отправка сообщений в Telegram Bot API не должна блокировать основной HTTP-запрос пользователя (например, загрузку отчёта или смену статуса). Событие ставится в фоновую задачу / очередь после успешного коммита транзакции в PostgreSQL.
2. **SLA доставки (`US-11`):** при доступном Telegram Bot API уведомление должно быть доставлено получателю не более чем за **10 секунд** с момента наступления бизнес-события.
3. **Graceful Degradation (`US-12`, `AC 12.2`):** если у целевого пользователя не привязан Telegram (`telegram_id / telegram_chat_id IS NULL`), либо уведомления отключены в настройках профиля, либо Telegram API недоступен — основная операция в веб-сервисе **завершается успешно без ошибок для клиента**.
4. **Единое имя бота:** задаётся через переменную окружения `TELEGRAM_BOT_USERNAME` (по умолчанию в `.env.example` — `LabFlowBot`; ссылки формируются динамически как `https://t.me/${TELEGRAM_BOT_USERNAME}?start=<token>`).
5. **Формат разметки и безопасность:** используется режим `parse_mode="HTML"`. Все пользовательские данные (`full_name`, `title`, `comment_text`, `file_name`) перед подстановкой в шаблон **обязательно экранируются** через `html.escape(...)`, чтобы спецсимволы (`<`, `>`, `&`) в комментариях или названиях работ не вызывали ошибку `400 Bad Request: can't parse entities` от Telegram API.

## 2. Каталог триггеров событий (Event Triggers)

### 2.1. Сводная матрица триггеров

| Код события (`event_type`) | Бизнес-триггер (Источник в API) | Получатель | Обязательность отправки | Приоритет |
|---|---|---|---|:---:|
| **`TG_LINK_SUCCESS`** | Успешное погашение токена привязки командой `/start <token>` (`POST /telegram/internal/bind`) | Инициатор (Студент или Преподаватель) | Синхронный ответ в чат сразу при привязке | Must |
| **`NEW_SUBMISSION`** | Загрузка файла отчёта студентом (`POST /submissions/{id}/upload`): первичная сдача (`not_started` / `in_progress` ➔ `submitted`) или повторная (`needs_work` ➔ `submitted`) | Преподаватель — автор работы (`lab_works.creator_id`); если не указан — все активные пользователи с ролью `teacher` | Асинхронно, если привязан Telegram и включены уведомления | Must |
| **`STATUS_CHANGED_ACCEPTED`** | Преподаватель перевёл работу в статус `accepted` (`PATCH /submissions/{id}/status`) | Студент — владелец сдачи (`student_submissions.student_id`) | Асинхронно, если привязан Telegram и включены уведомления | Must |
| **`STATUS_CHANGED_REWORK`** | Преподаватель перевёл работу в статус `needs_work` (`PATCH /submissions/{id}/status`, с обязательным `comment_text`) | Студент — владелец сдачи (`student_submissions.student_id`) | Асинхронно, если привязан Telegram и включены уведомления | Must |
| **`NEW_COMMENT`** | Преподаватель добавил отдельный комментарий (`POST /submissions/{id}/comments`) вне одновременного перевода статуса | Студент — владелец сдачи (`student_submissions.student_id`) | Асинхронно, если привязан Telegram и включены уведомления | Must |
| **`TG_UNLINK_INFO`** *(опц.)* | Отвязка Telegram в веб-интерфейсе (`DELETE /telegram/unlink`) | Инициатор | Информационное уведомление перед очисткой `chat_id` (или фиксация только в аудит-логе) | Could |

### 2.2. Исключения и правила анти-спама (Non-Triggers & Deduplication)
1. **Не вызывают уведомлений:**
   - Переход студента `not_started` ➔ `in_progress` («Взять в работу») — не генерирует уведомление преподавателю, чтобы не перегружать чат рутинными действиями.
   - Создание/редактирование лабораторной работы преподавателем (в MVP достаточно отображения в списке работ, хотя при расширении можно добавить `NEW_LAB_WORK`).
   - Самодействие (если пользователь сам себе оставил системную заметку).
2. **Дедупликация `STATUS_CHANGED_REWORK` и `NEW_COMMENT`:**
   - При вызове `PATCH /submissions/{id}/status` со статусом `needs_work` и обязательным полем `comment_text` текст замечания одновременно сохраняется в `comments` и передаётся в событии смены статуса.
   - Чтобы студент не получал **два дублирующих сообщения** подряд за одну секунду, при одновременной смене статуса и добавлении комментария в рамках одного запроса отправляется **одно объединённое уведомление `STATUS_CHANGED_REWORK`**, уже содержащее текст замечания преподавателя.
   - Отдельное событие `NEW_COMMENT` отправляется только при самостоятельном вызове `POST /submissions/{id}/comments`.

## 3. Спецификация текстов сообщений и переменных подстановки

### 3.1. Словарь переменных шаблона

| Переменная | Источник в БД | Формат / Правило подготовки |
|---|---|---|
| `{full_name}` | `users.full_name` | Экранированный HTML (`Иванов Иван`) |
| `{student_name}` | `student.full_name` | ФИО студента, экранированный HTML |
| `{teacher_name}` | `teacher.full_name` | ФИО преподавателя, экранированный HTML |
| `{group_name}` | `lab_works.group_name` / `users.group_name` | Например, `ВПР42` |
| `{work_number}` | `lab_works.order_num` / `work_number` | Целое число (`1`, `2`, ...) |
| `{work_title}` | `lab_works.title` | Тема работы, экранированный HTML |
| `{submitted_at}` | `student_submissions.submitted_at` | Локальное время МСК (`UTC+3`) в формате `ДД.ММ.ГГГГ ЧЧ:ММ` |
| `{file_name}` | `student_submissions.file_name` | Исходное имя загруженного файла, экранированный HTML |
| `{comment_text}` | `comments.text` | Экранированный HTML. Если длина `> 1000` символов, обрезается до 1000 символов с суффиксом `… (полный текст доступен в LabFlow)` — защита от лимита Telegram 4096 символов |
| `{app_url}` | Конфигурация фронтенда | Ссылка на веб-кабинет (опционально, в виде кнопки/ссылки при наличии публичного URL) |

### 3.2. Шаблон 1 — Успешная привязка Telegram (`TG_LINK_SUCCESS`)
**Триггер:** Пользователь перешёл по deep-link `https://t.me/<bot>?start=<token>` и токен успешно валидирован бэкендом.

**Шаблон (HTML):**
```html
✅ <b>Telegram успешно подключён к LabFlow!</b>

👤 Пользователь: {full_name}
🎓 Роль: {role_label}

Теперь вы будете оперативно получать уведомления о проверках и сдачах лабораторных работ.
```
*(Где `{role_label}` = `Студент (группа {group_name})` или `Преподаватель`).*

**Негативные ответы бота при `/start`:**
- `/start` без токена:
  `👋 Здравствуйте! Это бот уведомлений сервиса <b>LabFlow</b>. Для привязки аккаунта перейдите по персональной ссылке из раздела «Настройки профиля» на сайте.`
- Недействительный, уже использованный или просроченный (> 10 минут) токен:
  `⛔ Ссылка привязки недействительна или устарела. Пожалуйста, сгенерируйте новую ссылку в личном кабинете LabFlow.`

### 3.3. Шаблон 2 — Новая сдача или повторная сдача работы (`NEW_SUBMISSION`)
**Триггер:** Студент успешно загрузил файл отчёта (`POST /submissions/{id}/upload`).  
**Получатель:** Преподаватель.

**Вариант А — Первичная сдача (`is_resubmission = false`):**
```html
📥 <b>Новая сдача работы!</b>

👨‍🎓 <b>Студент:</b> {student_name} ({group_name})
📘 <b>Работа:</b> ЛР №{work_number} «{work_title}»
📎 <b>Файл:</b> <code>{file_name}</code>
🕒 <b>Дата сдачи:</b> {submitted_at}
```

**Вариант Б — Повторная сдача после доработки (`is_resubmission = true`):**
```html
🔄 <b>Повторная сдача работы после доработки!</b>

👨‍🎓 <b>Студент:</b> {student_name} ({group_name})
📘 <b>Работа:</b> ЛР №{work_number} «{work_title}»
📎 <b>Новый файл:</b> <code>{file_name}</code>
🕒 <b>Дата сдачи:</b> {submitted_at}
```

**Триггер:** Преподаватель перевёл сдачу в статус `accepted` (`PATCH /submissions/{id}/status`).  
**Получатель:** Студент.

**Шаблон (если передан опциональный комментарий):**

<blockquote>{comment_text}</blockquote>

Исправьте замечания и загрузите обновлённый отчёт в личном кабинете LabFlow.

## 4. Требования к журналу уведомлений, настройкам и Retry-логике (вход для WBS 4.5.2 и 4.5.3)

### 4.1. Журнал истории уведомлений (`notification_logs`)
Для реализации задачи [[wbs-4-5-2|4.5.2]] и обеспечения наблюдаемости/повторной отправки требуется таблица истории уведомлений со следующими логическими полями:

| Поле | Тип | Описание и назначение |
|---|---|---|
| `id` | PK (UUID / Int) | Идентификатор записи уведомления |
| `recipient_id` | FK (`users.id`) | Получатель уведомления |
| `submission_id` | FK (`student_submissions.id`, nullable) | Связанная карточка сдачи (для трассировки и отладки) |
| `event_type` | Enum / String(64) | `TG_LINK_SUCCESS`, `NEW_SUBMISSION`, `STATUS_CHANGED_ACCEPTED`, `STATUS_CHANGED_REWORK`, `NEW_COMMENT` |
| `message_text` | TEXT | Сформированный (или подготовленный) текст уведомления |
| `status` | Enum / String(32) | `pending` ➔ `retrying` ➔ `sent` / `failed` / `skipped` |
| `attempts` | Integer (default 0) | Количество выполненных попыток отправки |
| `last_error` | TEXT (nullable) | Текст/HTTP-код последней ошибки Telegram Bot API |
| `next_retry_at` | DateTime (TZ, nullable) | Запланированное время следующей попытки |
| `created_at` | DateTime (TZ) | Время постановки события в очередь |
| `sent_at` | DateTime (TZ, nullable) | Время фактической успешной доставки |

### 4.2. Настройки уведомлений пользователя (`wbs-4-5-4`, `wbs-4-5-5`)
Для поддержки настроек уведомлений в профиле на стороне БД (`users`) и API рекомендуется предусмотреть булев флаг:
- `notifications_enabled` (`boolean`, по умолчанию `true`) — общий переключатель «Получать уведомления в Telegram» (пользователь может временно выключить рассылку, не отвязывая Telegram-аккаунт).
- При `notifications_enabled = false` или отсутствии `telegram_chat_id` запись может либо не отправляться, либо фиксироваться со статусом `skipped` (без попыток вызова Telegram API).

### 4.3. Политика повторных попыток (Retry Policy) и обработка ошибок Telegram API

| Ответ / Ситуация Telegram Bot API | Класс ошибки | Поведение сервиса (`4.5.3`) | Итоговый статус в `notification_logs` |
|---|---|---|---|
| `200 OK` | Успех | Фиксация `sent_at`, завершение задачи | `sent` |
| `429 Too Many Requests` (`parameters.retry_after`) | Rate Limit (Временная) | Пауза ровно на `retry_after` секунд (+ 1 с джиттера); постановка на повтор (не сжигая счётчик или с отдельным лимитом до 3 повторов) | `retrying` ➔ `sent` / `failed` |
| `5xx` (500, 502, 503, 504), таймаут, сетевой сбой | Временная | Экспоненциальный backoff (до **3 попыток**): **5 с → 15 с → 45 с** | `retrying` ➔ `sent` / `failed` (после 3-й неудачной попытки) |
| `403 Forbidden: bot was blocked by the user` | Перманентная | Повторные попытки **не выполняются**; ошибка логируется; рекомендуется сбросить флаг доставки (`notifications_enabled = false` или пометка блокировки) | `failed` |
| `400 Bad Request: chat not found` | Перманентная | Повторные попытки **не выполняются**; ошибка логируется | `failed` |
| `400 Bad Request: can't parse entities` | Ошибка шаблона | Предотвращается `html.escape`; как fallback — повторная отправка plain-text без `parse_mode` | `sent` (fallback) / `failed` |

## 5. Критерии приёмки и тест-сценарии (вход для WBS 4.5.6)

| ID проверки | Сценарий | Ожидаемый результат | Связь с ТК QA |
|---|---|---|---|
| **FR-06.1** | Генерация ссылки и привязка аккаунта через `/start <token>` | `chat_id` сохранён в профиле, бот отвечает шаблоном `TG_LINK_SUCCESS`, статус на сайте обновлен | `TC-TG-001` |
| **FR-06.2** | Повторное/просроченное использование токена привязки (> 10 мин) | Токен отклонён (`400`), бот выводит сообщение об устаревшей ссылке | Дополнить в `4.5.6` |
| **FR-06.3** | Сдача и повторная сдача отчёта студентом | Преподаватель в течение 10 с получает `NEW_SUBMISSION` (первичное или с пометкой повторной сдачи) | `TC-TG-002` |
| **FR-06.4** | Выставление статусов `accepted` / `needs_work` | Студент в течение 10 с получает `STATUS_CHANGED_ACCEPTED` или `STATUS_CHANGED_REWORK` (с замечанием, без дублирующего `NEW_COMMENT`) | `TC-TG-003`, `TC-E2E-001`, `TC-E2E-002` |
| **FR-06.5** | Отдельный комментарий через `POST .../comments` | Студент получает уведомление `NEW_COMMENT` с корректным HTML-экранированием спецсимволов `<`, `>`, `&` | Дополнить в `4.5.6` |
| **FR-06.6** | Недоступность Telegram API / HTTP `429` | Основной запрос в веб-приложении не падает; сервис выполняет до 3 попыток retry (для `429` с учётом `retry_after`) и пишет результат в `notification_logs` | `TC-TG-004`, `TC-TG-005` |
| **FR-06.7** | Блокировка бота пользователем (`403`) или непривязанный/отключённый Telegram | Бизнес-операция в LabFlow завершается успешно (`AC 12.2`); при `403` от Telegram ретраи не зацикливаются | Дополнить в `4.5.6` |
