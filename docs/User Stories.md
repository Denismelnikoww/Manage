# Пользовательские истории (User Stories) и критерии приёмки — Проект LabFlow

**Задача ИСР:** 3.1.1. [Аналитик] Разработка Use Cases и декомпозиция на User Stories (студент / преподаватель)  
**Исполнитель:** Пашковский Владимир (Роль: Аналитик)  
**Период выполнения:** 26–28 октября 2026 г.  
**Продукт:** Веб-сервис трекинга лабораторных работ LabFlow  
**Статус документа:** Утверждено для проектирования БД, контрактов API и формирования тест-плана  
**Связанный документ:** [[Use Cases|Спецификация прецедентов (Use Cases)]]

---

## 1. Методология и формат описания

Все пользовательские истории сформулированы по шаблону Connextra:
> **Как** `<роль / актор>`,  
> **я хочу** `<действие / функциональность>`,  
> **чтобы** `<бизнес-ценность / результат>`.

- **Приоритизация:** по шкале **MoSCoW** (Must Have, Should Have, Could Have, Won't Have).
- **Критерии приёмки (Acceptance Criteria / Definition of Done):** детально описаны в нотации **Given — When — Then** для прямой трансляции в тест-кейсы QA-инженером.
- **Связь со сценариями:** каждая история напрямую трассируется к соответствующему прецеденту в [[Use Cases|Спецификации Use Cases]].

## 2. Пользовательские истории по модулям разработки

### Модуль 1: Аутентификация и авторизация (WBS 4.1)

#### **US-01: Авторизация по ролям (Студент / Преподаватель)**
- **Как** зарегистрированный пользователь сервиса,  
  **я хочу** войти в систему по логину/паролю и получить интерфейс, соответствующий моей роли,  
  **чтобы** иметь доступ только к разрешенным функциям (студент — к сдаче, преподаватель — к проверке).
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-01: Аутентификация и авторизация в сервисе|UC-01]]
- **Критерии приёмки (Acceptance Criteria):**
  - **AC 1.1:** *Given* пользователь вводит валидный email и пароль студента, *When* нажимает кнопку «Войти», *Then* бэкенд возвращает JWT с клеймом `role: student`, открывается студенческий дашборд.
  - **AC 1.2:** *Given* пользователь вводит данные преподавателя, *When* нажимает кнопку «Войти», *Then* открывается панель преподавателя с возможностью управления работами и ведомостью.
  - **AC 1.3:** *Given* студент пытается вручную обратиться к эндпоинту создания работ `POST /api/v1/labs`, *When* отправляется запрос с токеном студента, *Then* сервер возвращает ошибку `403 Forbidden`.

### Модуль 2: Управление лабораторными работами и дедлайнами (WBS 4.2)

#### **US-02: Создание и публикация лабораторной работы**
- **Как** преподаватель,  
  **я хочу** создать новую лабораторную работу с указанием темы, описания и дедлайна для группы ВПР42,  
  **чтобы** студенты вовремя узнали задание и сроки сдачи.
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-02: Управление лабораторными работами (CRUD)|UC-02]]
- **Критерии приёмки (Acceptance Criteria):**
  - **AC 2.1:** Поля «Название», «Описание», «Дедлайн» и «Группа» обязательны к заполнению.
  - **AC 2.2:** Дата дедлайна не может быть в прошлом.
  - **AC 2.3:** После нажатия «Создать» работа сохраняется в БД, и для каждого студента группы автоматически создается запись сдачи со статусом `Не начата`.

#### **US-03: Редактирование и удаление лабораторной работы**
- **Как** преподаватель,  
  **я хочу** иметь возможность отредактировать параметры работы (например, продлить дедлайн) или удалить ошибочно созданную работу,  
  **чтобы** поддерживать актуальность учебного плана.
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-02: Управление лабораторными работами (CRUD)|UC-02]]
- **Критерии приёмки:**
  - **AC 3.1:** При продлении дедлайна новое время мгновенно обновляется у всех студентов группы.
  - **AC 3.2:** При попытке удаления работы система запрашивает подтверждение модальным окном («Вы уверены?»).

#### **US-04: Просмотр списка работ с дедлайнами и фильтрами**
- **Как** студент,  
  **я хочу** видеть сводный список всех лабораторных работ с датами сдачи и своими текущими статусами,  
  **чтобы** планировать нагрузку и не пропускать сроки.
- **Приоритет:** Must Have (базовый список) / Should Have (фильтрация по статусу)
- **Связанный Use Case:** [[Use Cases#UC-03: Просмотр списка работ и дедлайнов студентом|UC-03]]
- **Критерии приёмки:**
  - **AC 4.1:** Список отображает название, дедлайн и цветной бейдж статуса (`Не начата`, `В работе`, `Сдана`, `На доработке`, `Принята`).
  - **AC 4.2:** Если до дедлайна осталось менее 3 дней, дата подсвечивается предупреждающим цветом (желтый); если дедлайн прошел — красным.
  - **AC 4.3:** Доступен быстрый фильтр по статусам (например, показать только требующие действия: `На доработке` и `В работе`).

### Модуль 3: Статусы работ (WBS 4.3)

#### **US-05: Взятие работы в выполнение студентом**
- **Как** студент,  
  **я хочу** перевести работу из статуса «Не начата» в «В работе»,  
  **чтобы** преподаватель и я сам видели, что выполнение начато.
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-03: Просмотр списка работ и дедлайнов студентом|UC-03]], [[Use Cases#UC-04: Сдача отчёта по лабораторной работе|UC-04]]
- **Критерии приёмки:**
  - **AC 5.1:** Для работы со статусом `Не начата` доступна кнопка «Взять в работу».
  - **AC 5.2:** По клику отправляется `PATCH /api/v1/submissions/{id}/status`, статус без перезагрузки экрана меняется на `В работе`.

### Модуль 4: Загрузка отчетов и рецензирование (WBS 4.4)

#### **US-06: Загрузка файла отчета студентом**
- **Как** студент,  
  **я хочу** загрузить файл отчета (PDF/DOCX/ZIP) в карточку лабораторной работы,  
  **чтобы** отправить его преподавателю на проверку.
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-04: Сдача отчёта по лабораторной работе|UC-04]]
- **Критерии приёмки:**
  - **AC 6.1:** Поддерживается загрузка файлов через выбор в проводнике и drag-and-drop.
  - **AC 6.2:** Валидация формата (.pdf, .docx, .zip) и лимита объема (до 20 МБ) на клиенте и сервере.
  - **AC 6.3:** При успешной отправке файл загружается в бакет MinIO, статус автоматически переходит в `Сдана`, фиксируется timestamp сдачи.
  - **AC 6.4:** После успешной сдачи форма загрузки блокируется до вердикта преподавателя.

#### **US-07: Просмотр ведомости сдачи и скачивание отчетов преподавателем**
- **Как** преподаватель,  
  **я хочу** видеть журнал сдачи группы и иметь возможность скачать файл отчета любого студента,  
  **чтобы** проверить качество выполненной работы.
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-05: Проверка сданных работ и ведомость группы (Преподаватель)|UC-05]]
- **Критерии приёмки:**
  - **AC 7.1:** Ведомость отображает список студентов группы ВПР42 со статусами по каждой работе.
  - **AC 7.2:** Работы со статусом `Сдана` выделены контрастным индикатором «Требует проверки».
  - **AC 7.3:** Клик по кнопке «Скачать» генерирует защищенную ссылку MinIO pre-signed URL; файл открывается или сохраняется без раскрытия прямых публичных доступов к хранилищу.

#### **US-08: Рецензирование и выставление статуса («Принята» / «На доработке»)**
- **Как** преподаватель,  
  **я хочу** оставить текстовый комментарий к сданному отчету и изменить статус на «Принята» или «На доработке»,  
  **чтобы** студент узнал результат проверки и при необходимости исправил ошибки.
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-06: Комментирование и выставление вердикта|UC-06]]
- **Критерии приёмки:**
  - **AC 8.1:** При выборе вердикта «На доработке» поле ввода комментария является строго обязательным (минимум 5 символов).
  - **AC 8.2:** При выборе «Принята» работа фиксируется в финальном успешном статусе.
  - **AC 8.3:** Студент видит оставленный комментарий в карточке работы в блоке «Замечания преподавателя».

#### **US-09: Повторная сдача работы после доработки**
- **Как** студент, чья работа переведена в статус «На доработке»,  
  **я хочу** ознакомиться с комментариями, прикрепить исправленный файл отчета и повторно отправить работу,  
  **чтобы** закрыть долг и получить статус «Принята».
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-04: Сдача отчёта по лабораторной работе|UC-04]], [[Use Cases#UC-06: Комментирование и выставление вердикта|UC-06]]
- **Критерии приёмки:**
  - **AC 9.1:** Кнопка повторной загрузки файла разблокируется только при статусе `На доработке`.
  - **AC 9.2:** При загрузке нового файла старый файл в MinIO архивируется/перезаписывается с новой меткой времени, а статус возвращается в `Сдана`.

### Модуль 5: Telegram-интеграция и уведомления (WBS 4.5)

#### **US-10: Привязка Telegram-аккаунта через бота**
- **Как** пользователь (студент или преподаватель),  
  **я хочу** в один клик привязать свой Telegram-аккаунт через бота по персональной ссылке,  
  **чтобы** оперативно получать сообщения о проверках и сдачах без необходимости держать открытым веб-сайт.
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-07: Привязка Telegram-аккаунта|UC-07]]
- **Критерии приёмки:**
  - **AC 10.1:** В личном кабинете генерируется уникальная ссылка на Telegram-бота с одноразовым токеном (`/start <token>`).
  - **AC 10.2:** При нажатии кнопки «Старт» в боте бэкенд связывает `telegram_chat_id` с аккаунтом пользователя.
  - **AC 10.3:** В профиле на сайте мгновенно отображается статус подключения: «Telegram подключен».

#### **US-11: Мгновенные Telegram-уведомления студенту**
- **Как** студент,  
  **я хочу** получать сообщение в Telegram в момент, когда преподаватель проверил мою работу (принял или оставил замечания),  
  **чтобы** оперативно узнать оценку или приступить к исправлению ошибок.
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-08: Доставка уведомлений через Telegram-бота|UC-08]]
- **Критерии приёмки:**
  - **AC 11.1:** При переходе работы в `На доработке` бот присылает сообщение с названием работы и текстом замечания преподавателя в течение 10 секунд.
  - **AC 11.2:** При переходе в `Принята` бот присылает подтверждающее сообщение об успешной защите.

#### **US-12: Telegram-уведомления преподавателю о новых сдачах**
- **Как** преподаватель,  
  **я хочу** получать уведомление в Telegram о том, что студент сдал или повторно отправил отчет,  
  **чтобы** своевременно проверить поступившие материалы.
- **Приоритет:** Must Have
- **Связанный Use Case:** [[Use Cases#UC-08: Доставка уведомлений через Telegram-бота|UC-08]]
- **Критерии приёмки:**
  - **AC 12.1:** При успешной отправке отчета студентом бот направляет преподавателю сообщение с ФИО студента, группой и темой работы.
  - **AC 12.2:** Если преподаватель отключил уведомления или не привязал Telegram, система продолжает штатно функционировать без ошибок на клиенте.

## 4. Резюме для участников команды разработки

1. **Для Lead Dev (Паршин А.) & Backend (Теплов А.):**
   - Роли зафиксированы в JWT (`student`, `teacher`).
   - Переходы между 5 статусами строго детерминированы матрицей жизненного цикла (см. [[Use Cases#3. Матрица жизненного цикла статусов лабораторной работы|матрицу статусов в Use Cases]]).
   - Загрузка файлов изолирована в бакете MinIO `submissions/`, отдача — исключительно через временные pre-signed URL.
   - Сервис aiogram3 слушает события смены статусов и новых файлов без блокировки HTTP-потока.
2. **Для Frontend (Пашковский В.):**
   - Разграничение представлений: студенту — персональный список и форма сдачи; преподавателю — журнал/ведомость группы ВПР42 с возможностью скачивания и модальным окном рецензирования.
   - Обязательная валидация расширений (PDF/DOCX/ZIP) и размера файла (< 20 МБ) до отправки на бэкенд.
3. **Для QA (Кулов Д.):**
   - Все 12 User Stories содержат четкие приемочные критерии (Acceptance Criteria), готовые для прямой конвертации в тест-кейсы и приемочные сценарии для вехи «Проектирование завершено» (WBS 5.1.1).
