## 4. Техническая разработка — функциональные модули

### 4.1. Модуль «Аутентификация и авторизация»

- 4.1.1. [Аналитик] Сценарии входа/регистрации, разграничение ролей «студент» / «преподаватель», требования к безопасности сессий.
- 4.1.2. [Backend / PM] Проектирование структуры таблиц users / roles, разработка API регистрации и входа, хеширование паролей.
- 4.1.3. [Backend] Реализация проверки прав доступа по ролям, защита эндпоинтов.
- 4.1.4. [Frontend] Вёрстка формы входа/регистрации по макету (React + SCSS).
- 4.1.5. [Frontend] Интеграция формы с API аутентификации, обработка ошибок и хранение токена.
- 4.1.6. [QA] Чек-лист и тест-кейсы: позитивные/негативные сценарии, попытки обхода ролей, слабые пароли, утечка сессий.
- 4.1.7. [QA] Функциональное тестирование модуля, заведение баг-репортов и верификация исправлений.

### 4.2. Модуль «Работы и дедлайны»

- 4.2.1. [Аналитик] Use Cases CRUD работ, правила дедлайнов, привязка к учебной группе.
- 4.2.2. [Backend / PM] Проектирование таблиц и разработка CRUD API.
- 4.2.3. [Backend] Реализация API фильтрации/сортировки работ по статусу и дедлайну.
- 4.2.4. [Frontend] Вёрстка списка работ, карточки работы, формы создания/редактирования (только для преподавателя).
- 4.2.5. [Frontend] Интеграция UI с API работ и дедлайнов; отображение дедлайнов и статусов.
- 4.2.6. [QA] Тест-кейсы CRUD, граничные случаи дедлайнов, права доступа (студент не может создавать/редактировать).
- 4.2.7. [QA] Функциональное тестирование, баг-репорты, верификация.

### 4.3. Модуль «Статусы работ»

- 4.3.1. [Аналитик] Матрица переходов статусов, кто и когда может менять.
- 4.3.2. [Backend / PM] Проектирование таблицы истории статусов (Could), разработка API смены статуса с проверкой прав.
- 4.3.3. [Frontend] Вёрстка UI смены статуса (для преподавателя) и отображения текущего статуса (для студента).
- 4.3.4. [Frontend] Интеграция с API статусов, обновление списка без перезагрузки.
- 4.3.5. [QA] Тест-кейсы на все 5 статусов, недопустимые переходы, права доступа, история изменений.
- 4.3.6. [QA] Функциональное тестирование, баг-репорты, верификация.

### 4.4. Модуль «Отчёты и комментарии»

- 4.4.1. [Аналитик] Требования к загрузке/скачиванию файлов, политики доступа (pre-signed URL), ограничения по типам/размерам.
- 4.4.2. [Backend / PM] Проектирование таблиц reports / comments, настройка бакетов MinIO и политик доступа.
- 4.4.3. [Backend] Разработка API загрузки/скачивания отчёта (MinIO) и комментирования преподавателем.
- 4.4.4. [Frontend] Вёрстка UI загрузки файла, списка отчётов и блока комментариев.
- 4.4.5. [Frontend] Интеграция с API отчётов и комментариев, индикация загрузки/ошибок.
- 4.4.6. [QA] Тест-кейсы загрузки/скачивания, права доступа к файлам, целостность файлов, комментарии.
- 4.4.7. [QA] Функциональное тестирование, баг-репорты, верификация.

### 4.5. Модуль «Telegram-уведомления»

- 4.5.1. [Аналитик] Проектирование триггеров (смена статуса, новый комментарий, новая сдача) и текстов сообщений.
- 4.5.2. [Backend / PM] Проектирование структуры таблицы истории уведомлений, настройка aiogram3-бота.
- 4.5.3. [Backend] Разработка API привязки Telegram и сервиса отправки уведомлений студенту и преподавателю; retry-логика и очередь.
- 4.5.4. [Frontend] Вёрстка UI привязки Telegram-аккаунт и настроек уведомлений.
- 4.5.5. [Frontend] Интеграция UI привязки Telegram с бэкендом.
- 4.5.6. [QA] Чек-лист и тест-кейсы доставки уведомлений, отказоустойчивость при недоступном API, повторы.
- 4.5.7. [QA] Функциональное тестирование, баг-репорты, верификация.

### 4.6. Интеграция модулей и сквозные сценарии

- 4.6.1. [Аналитик / Lead Dev] Сверка OpenAPI-контрактов и общих схем данных между модулями.
- 4.6.2. [Backend] Связывание backend-модулей: Auth, работы, статусы, отчёты и Telegram; проверка передачи событий и прав.
- 4.6.3. [Frontend / Backend] Сквозная интеграция интерфейсов с API backend по сценариям студента и преподавателя.
- 4.6.4. [QA + вся команда] Сквозное E2E-тестирование связки фронт—API—backend и исправление интеграционных дефектов.

## 5. Тестирование, качество и приёмка

- 5.1.1. [QA] Составление тест-плана и черновиков тест-кейсов по ключевым сценариям на вехе «Проектирование завершено».
- 5.1.2. [QA] Smoke-тест-кейсы развёртывания (`docker compose up` на чистой машине).
- 5.1.3. [QA + вся команда] Регрессионный набор тест-кейсов, прогон по всем сценариям на каждой вехе и исправление найденных дефектов.
- 5.1.4. [QA + Аналитик] Трассировка требований к тест-кейсам, ревизия на вехе «Качество и развёртывание».
- 5.1.5. [Вся команда] Приёмка по критериям SMART: 0 критичных дефектов, 100% сценариев покрыты, отклонение по срокам ≤ 1 недели.
- 5.1.6. [QA + PM] Подготовка результатов тестирования для подтверждения приёмки на защите.
