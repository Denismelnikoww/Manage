## 1. Структура веток (Модель ветвления Git-flow)

В проекте используется адаптированная модель ветвления **Git-flow**. Работа ведётся через две постоянные ветки и вспомогательные временные ветки.

### 1.1. Постоянные ветки
- `main` — **Релизная ветка**. Содержит только проверенный, протестированный и стабильный код, готовый к защите лабораторных работ и демонстрации заказчику. Прямой пуш в `main` строго **запрещен**. Код попадает в `main` только через Pull Request из `develop` или `hotfix/*`.
- `develop` — **Основная ветка интеграции**. Содержит актуальное состояние разработки текущего спринта/вехи. Все новые функции и доработки вливаются сюда через Pull Request. Прямой пуш в `develop` **запрещен**.

### 1.2. Временные ветки
- `feature/<название-задачи>` — ветки для разработки новых функций (создаются от `develop`, вливаются обратно в `develop`).
- `bugfix/<название-исправления>` — ветки для устранения дефектов, выявленных в процессе интеграции и тестирования в `develop`.
- `hotfix/<название-исправления>` — ветки для критических срочных правок стабильного релиза (создаются от `main`, вливаются одновременно в `main` и в `develop`).
- `release/vX.Y.Z` — ветки стабилизации перед защитой контрольной вехи или демонстрацией релиза.

```
(main)       ●─────────────────────────────────● (v1.0 Release)
              \                               /
(hotfix)       \                     ●───────●
                \                   /       /
(develop)        ●────────●────────●───────● (Integration)
                  \      /  \     /
(feature/wbs-...)  ●────●    ●───●
```

## 2. Правила именования веток

Имя временной ветки формируется в нижнем регистре (kebab-case) с обязательным указанием типа ветки и номера задачи по WBS:

- `feature/wbs-4-2-2-crud-works` — разработка CRUD API работ
- `feature/wbs-4-1-2-auth-api` — разработка API аутентификации
- `feature/wbs-4-1-4-login-form` — вёрстка форм входа
- `fix/wbs-4-2-date-validation` — исправление валидации дедлайнов
- `docs/wbs-2-1-1-git-flow` — обновление документации
- `ci/wbs-2-2-1-github-actions` — настройка CI-пайплайна

## 3. Стандарт сообщений коммитов (Conventional Commits)

Все коммиты должны следовать стандарту **Conventional Commits**:

```
<тип>(<область>): <краткое описание в повелительном наклонении>

[необязательное тело коммита с подробным объяснением]

[необязательный футер: Closes #номер-задачи / Refs WBS]
```

### Разрешенные типы коммитов:
- `feat` — добавление новой функциональности (например, `feat(backend): add CRUD endpoints for labs`)
- `fix` — исправление ошибки/бага (`fix(auth): fix JWT expiration handling`)
- `docs` — изменения только в документации (`docs(wbs): update git-flow specification`)
- `style` — форматирование, пробелы, точки с запятой, не влияющие на логику
- `refactor` — рефакторинг кода без добавления функционала и без исправления багов
- `test` — добавление или исправление тестов (`test(works): add tests for lab creation`)
- `ci` — изменения в конфигурации CI/CD скриптов (`ci(github): add workflow for frontend build`)
- `chore` — рутинные задачи, обновление зависимостей (`chore(deps): bump vite version`)

## 4. Регламент Code Review и создания Pull Request (PR)

1. **Создание PR:**
   - PR создаётся из ветки `feature/*` в ветку `develop`.
   - Заголовок PR должен кратко отражать суть: `feat(works): реализация CRUD API для работ [WBS 4.2.2]`.
   - Описание PR оформляется строго по утверждённому шаблону `.github/pull_request_template.md`.
2. **Требования к прохождению ревью:**
   - **Lead Dev / ревьюер** проверяет архитектуру, соответствие кодстайлу, отсутствие дублирования и соблюдение DoD.
   - Обязателен минимум **1 положительный review approval** перед слиянием.
   - Все замечания ревьюера должны быть устранены (Resolved conversation).
3. **Требования к автопроверкам:**
   - Все проверки автоматизированного CI-пайплайна (`GitHub Actions`) должны завершиться со статусом **Success** (зелёная галочка).
4. **Стратегия слияния (Merge Strategy):**
   - Используется **Squash and Merge** для сохранения чистой истории в ветке `develop`.

## 5. Политика защиты веток (Branch Protection Rules)

Для защиты репозитория от случайной порчи кодовой базы и обеспечения контроля качества установлены правила защиты веток `main` и `develop`:

| Параметр настройки GitHub | `main` | `develop` |
| ------------------------- | ------ | --------- |
| **Require a pull request before merging** | ✅ Включено | ✅ Включено |
| **Require approvals** | 1 approval (Lead Dev / Backend) | 1 approval (Peer Review / Lead) |
| **Dismiss stale pull request approvals when new commits are pushed** | ✅ Включено | ✅ Включено |
| **Require status checks to pass before merging** (CI) | ✅ Включено | ✅ Включено |
| **Require branches to be up to date before merging** | ✅ Включено | ✅ Включено |
| **Do not allow bypassing the above settings** (включая админов) | ✅ Включено | ✅ Включено |
| **Restrict who can push to matching branches** (прямой push) | ❌ Заблокирован | ❌ Заблокирован |
| **Allow force pushes** | ❌ Запрещен | ❌ Запрещен |
| **Allow deletions** | ❌ Запрещен | ❌ Запрещен |

### Инструкция по применению настроек в GitHub:
1. Перейти в репозиторий: `Settings` → `Branches`.
2. Нажать **Add branch protection rule**.
3. В поле **Branch name pattern** указать `main`, выставить флаги из таблицы выше и сохранить.
4. Повторить процедуру для `develop`.
