## 1. Контекст, цели и границы MVP (Scope)

Документ фиксирует детальные пользовательские сценарии (Use Cases) веб-сервиса **LabFlow**.
Функционал строго ограничен рамками **MVP** для одной академической группы (ВПР42) без раздувания второстепенными фичами:
- **Ролевая модель:** строго две роли — «Студент» и «Преподаватель».
- **Жизненный цикл работы:** ровно 5 детерминированных статусов (`Не начата` ➔ `В работе` ➔ `Сдана` ➔ `На доработке` ➔ `Принята`).
- **Файловое хранилище:** загрузка отчетов студентом в MinIO (PDF/DOCX/ZIP до 20 МБ) и безопасное скачивание преподавателем по pre-signed URL.
- **Обратная связь:** текстовые комментарии преподавателя к сданной работе.
- **Интеграция:** Telegram Bot API для уведомлений о ключевых событиях с механизмом retry.
- **Исключено из MVP (Out of Scope):** групповая сдача одной работы командой из нескольких человек, автоматический запуск/тестирование кода студентов (CI runner), интеграция с электронным деканатом/Moodle, чат в реальном времени.

## 2. Модель акторов (Actors)

| Актор                         | Описание и область ответственности                                                                                                                                                                                                                 |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Студент**                   | Пользователь с ролью обучающегося группы ВПР42. Просматривает назначенные работы и дедлайны, изменяет статус работы на «В работе», загружает файлы отчетов, знакомится с рецензиями преподавателя, привязывает Telegram для получения нотификаций. |
| **Преподаватель**             | Пользователь с ролью проверяющего/ведущего курс. Создает, редактирует и удаляет карточки лабораторных работ, просматривает общую ведомость группы, скачивает отчеты, выставляет вердикт («Принята» / «На доработке») и пишет комментарии.          |
| **Система (Telegram-сервис)** | Фоновый компонент бэкенда на базе `aiogram3`, отслеживающий бизнес-события сервиса и доставляющий персонализированные сообщения в Telegram.                                                                                                        |

## 3. Матрица жизненного цикла статусов лабораторной работы

Сдача лабораторной работы каждым студентом проходит через конечный автомат:

```
                  ┌──────────────────────┐
                  │      Не начата       │
                  └──────────┬───────────┘
                             │ (студент берёт в работу)
                             ▼
                  ┌──────────────────────┐
        ┌────────>│       В работе       │<────────┐
        │         └──────────┬───────────┘         │
        │                    │ (студент сдаёт файл)│
        │                    ▼                     │
        │         ┌──────────────────────┐         │
        │         │        Сдана         │         │
        │         └──────────┬───────────┘         │
        │                    │                     │
(преподаватель               │ (преподаватель      │ (преподаватель
отклоняет работу)            │  одобряет работу)   │  отклоняет работу)
        │                    ▼                     │
        │         ┌──────────────────────┐         │
        └─────────┤     На доработке     ├─────────┘
                  └──────────────────────┘
                             │
                             ▼ (студент устраняет замечания и перезагружает файл ➔ Сдана)
                  ┌──────────────────────┐
                  │       Принята        │ (Финальное состояние)
                  └──────────────────────┘
```

| Исходный статус | Целевой статус | Кто инициирует | Условие перехода |
|---|---|:---:|---|
| — | **Не начата** | Преподаватель / Система | Автоматически при создании работы для группы или регистрации студента |
| Не начата | **В работе** | Студент | Студент нажимает кнопку «Взять в работу» |
| Не начата / В работе / На доработке | **Сдана** | Студент | Студент прикрепляет файл отчета и нажимает «Отправить на проверку» |
| Сдана | **На доработке** | Преподаватель | Преподаватель оставляет комментарий с замечаниями и отклоняет отчет |
| Сдана | **Принята** | Преподаватель | Преподаватель подтверждает соответствие отчета требованиям |

## 4. Спецификация прецедентов (Use Cases)

### UC-01: Аутентификация и авторизация в сервисе
- **Актор:** Студент, Преподаватель.
- **Приоритет:** Must Have.
- **Связанная история:** [[User Stories#US-01: Авторизация по ролям (Студент / Преподаватель)|US-01]]
- **Предусловие:** Пользователь открыл главную страницу веб-приложения.
- **Триггер:** Пользователь нажимает «Войти» или «Зарегистрироваться».
- **Основной сценарий (Main Flow):**
  1. Пользователь вводит email/логин и пароль.
  2. При первой регистрации пользователь выбирает роль («Студент» или «Преподаватель») и группу (для студента — ВПР42).
  3. Клиент отправляет запрос на эндпоинт аутентификации.
  4. Бэкенд валидирует учетные данные, проверяет хеш пароля в PostgreSQL и генерирует JWT-токен с полезной нагрузкой роли (`role: student | teacher`).
  5. Клиент сохраняет токен в безопасном хранилище и перенаправляет пользователя в личный кабинет согласно роли.
- **Альтернативные сценарии и исключения:**
  - *Неверные учетные данные:* Бэкенд возвращает HTTP 401 Unauthorized. UI выводит подсказку «Неверный логин или пароль».
  - *Истечение срока JWT:* При истечении срока действия токена пользователь автоматически перенаправляется на форму логина с сообщением о необходимости повторного входа.
- **Постусловие:** Пользователь авторизован; все дальнейшие запросы содержат заголовок `Authorization: Bearer <token>`.

### UC-02: Управление лабораторными работами (CRUD)
- **Актор:** Преподаватель.
- **Приоритет:** Must Have.
- **Связанные истории:** [[User Stories#US-02: Создание и публикация лабораторной работы|US-02]], [[User Stories#US-03: Редактирование и удаление лабораторной работы|US-03]]
- **Предусловие:** Преподаватель успешно авторизован в системе.
- **Триггер:** Преподаватель переходит в панель управления работами и нажимает «Создать лабораторную работу» (либо выбирает редактирование/удаление существующей).
- **Основной сценарий:**
  1. Преподаватель заполняет форму: порядковый номер, название («ЛР №1: Основы Git»), подробное описание/требования, дату и время дедлайна, учебную группу.
  2. Преподаватель нажимает «Опубликовать».
  3. Бэкенд создает запись в таблице `lab_works` и автоматически инициализирует записи в таблице `student_submissions` для всех студентов группы ВПР42 со статусом `Не начата`.
  4. Новая работа отображается в общем списке работ группы.
- **Альтернативные сценарии:**
  - *Редактирование:* Преподаватель корректирует формулировку задания или сдвигает дедлайн. Изменения сохраняются и сразу видны студентам.
  - *Удаление:* Преподаватель подтверждает удаление работы. Если по работе уже есть сданные отчеты, система запрашивает явное подтверждение (soft delete).
- **Постусловие:** Лабораторная работа доступна студентам группы ВПР42 для сдачи.

### UC-03: Просмотр списка работ и дедлайнов студентом
- **Актор:** Студент.
- **Приоритет:** Must Have (фильтрация и сортировка — Should Have).
- **Связанные истории:** [[User Stories#US-04: Просмотр списка работ с дедлайнами и фильтрами|US-04]], [[User Stories#US-05: Взятие работы в выполнение студентом|US-05]]
- **Предусловие:** Студент авторизован в системе.
- **Триггер:** Переход в раздел «Мои лабораторные работы».
- **Основной сценарий (Main Flow):**
  1. Система загружает список всех лабораторных работ, назначенных группе ВПР42.
  2. Для каждой работы выводятся: номер и тема, дата дедлайна, индикатор срочности (до дедлайна осталось < 3 дней / просрочено), персональный текущий статус студента (`Не начата`, `В работе`, `Сдана`, `На доработке`, `Принята`).
  3. Студент может отфильтровать список по статусу или отсортировать по дате дедлайна (ближайшие сверху).
- **Постусловие:** Студент получил наглядную картину своей академической успеваемости.

### UC-04: Сдача отчёта по лабораторной работе
- **Актор:** Студент.
- **Приоритет:** Must Have.
- **Связанные истории:** [[User Stories#US-06: Загрузка файла отчета студентом|US-06]], [[User Stories#US-09: Повторная сдача работы после доработки|US-09]]
- **Предусловие:** Студент открыл карточку конкретной лабораторной работы; статус работы: `Не начата`, `В работе` или `На доработке`.
- **Триггер:** Студент выбирает файл отчета и нажимает «Отправить на проверку».
- **Основной сценарий (Main Flow):**
  1. Студент перетаскивает файл (PDF, DOCX, ZIP; размер до 20 МБ) в область загрузки.
  2. Клиент проводит первичную валидацию (формат, размер).
  3. Файл отправляется на бэкенд, который сохраняет его в бакет MinIO по уникальному ключу пути: `submissions/{lab_id}/{student_id}/{timestamp}_{filename}`.
  4. В БД обновляется запись сдачи: путь к файлу в MinIO, дата/время сдачи, статус меняется на `Сдана`.
  5. Генерируется внутреннее событие `NEW_SUBMISSION` для сервиса Telegram-уведомлений.
  6. Интерфейс студента обновляет статус работы на `Сдана` (зеленый бейдж) и блокирует повторную отправку до проверки преподавателем.
- **Исключения:**
  - *Недопустимый формат файла или размер > 20 МБ:* Загрузка отклоняется, выводится сообщение: «Допустимы файлы PDF, DOCX, ZIP размером не более 20 МБ».
  - *Сбой хранилища MinIO:* Система возвращает HTTP 500, транзакция БД откатывается, пользователю выводится: «Ошибка при сохранении файла. Попробуйте еще раз».
- **Постусловие:** Файл сохранен в MinIO; статус переведен в `Сдана`; инициировано уведомление преподавателю.

### UC-05: Проверка сданных работ и ведомость группы (Преподаватель)
- **Актор:** Преподаватель.
- **Приоритет:** Must Have.
- **Связанная история:** [[User Stories#US-07: Просмотр ведомости сдачи и скачивание отчетов преподавателем|US-07]]
- **Предусловие:** Преподаватель авторизован в системе.
- **Триггер:** Преподаватель переходит во вкладку «Ведомость сдачи» / «Проверка работ».
- **Основной сценарий (Main Flow):**
  1. Система отображает сводную таблицу (студенты группы ВПР42 по строкам, лабораторные работы по колонкам) с цветовой индикацией статусов.
  2. Преподаватель видит бейджи сданных работ, требующих проверки (`Сдана`).
  3. Преподаватель кликает по ячейке сдачи конкретного студента — открывается карточка проверки с информацией о дате загрузки и ссылкой на файл.
  4. При нажатии на «Скачать отчёт» система генерирует временный безопасный pre-signed URL из MinIO со сроком жизни 15 минут, и файл скачивается в браузере.
- **Постусловие:** Преподаватель ознакомился с содержимым отчета студента.

### UC-06: Комментирование и выставление вердикта
- **Актор:** Преподаватель.
- **Приоритет:** Must Have.
- **Связанные истории:** [[User Stories#US-08: Рецензирование и выставление статуса («Принята» / «На доработке»)|US-08]], [[User Stories#US-09: Повторная сдача работы после доработки|US-09]]
- **Предусловие:** Преподаватель находится в карточке проверки отчета студента (текущий статус: `Сдана`).
- **Триггер:** Преподаватель нажимает кнопку «Принять» или «Отправить на доработку».
- **Основной сценарий 1 (Принятие работы):**
  1. Преподаватель при необходимости вводит опциональный комментарий («Отличная работа, замечаний нет»).
  2. Нажимает «Принять работу».
  3. Статус работы в БД обновляется на `Принята`.
  4. Формируется событие `STATUS_CHANGED_ACCEPTED`.
- **Основной сценарий 2 (Отправка на доработку):**
  1. Преподаватель вводит обязательный текстовый комментарий с перечнем замечаний (например, «Исправить выводы в разделе 3, добавить скриншот работы эмулятора»).
  2. Нажимает «Отправить на доработку».
  3. Статус работы в БД обновляется на `На доработке`.
  4. Формируется событие `STATUS_CHANGED_REWORK` и `NEW_COMMENT`.
- **Альтернативные сценарии:**
  - *Попытка вернуть на доработку без комментария:* Система блокирует действие и подсвечивает поле ввода комментария («Укажите причину отправки на доработку»).
- **Постусловие:** Статус зафиксирован; комментарий сохранен в БД; сгенерировано событие нотификации для студента.

### UC-07: Привязка Telegram-аккаунта
- **Актор:** Студент, Преподаватель.
- **Приоритет:** Must Have.
- **Связанная история:** [[User Stories#US-10: Привязка Telegram-аккаунта через бота|US-10]]
- **Предусловие:** Пользователь авторизован в LabFlow и имеет аккаунт в Telegram.
- **Триггер:** Переход в «Настройки профиля» ➔ «Уведомления в Telegram».
- **Основной сценарий (Main Flow):**
  1. Пользователь нажимает кнопку «Привязать Telegram».
  2. Система генерирует уникальный одноразовый deep-link токен вида `https://t.me/LabFlowNotifierBot?start=AUTH_TOKEN_XYZ`.
  3. Пользователь переходит по ссылке в Telegram-бота и нажимает `/start`.
  4. Бот валидирует токен через бэкенд LabFlow и сохраняет `telegram_chat_id` пользователя в профиле.
  5. Бот отправляет приветственное сообщение: «✅ Ваш Telegram успешно подключен к LabFlow! Вы будете получать уведомления о статусах работ».
  6. В веб-интерфейсе статус меняется на «Telegram подключен (@username)».
- **Постусловие:** `telegram_chat_id` привязан к аккаунту пользователя для отправки асинхронных уведомлений.

---

### UC-08: Доставка уведомлений через Telegram-бота
- **Актор:** Система (Telegram-сервис на aiogram3).
- **Приоритет:** Must Have (надежность с retry — Should Have).
- **Связанные истории:** [[User Stories#US-11: Мгновенные Telegram-уведомления студенту|US-11]], [[User Stories#US-12: Telegram-уведомления преподавателю о новых сдачах|US-12]]
- **Предусловие:** Произошло бизнес-событие в сервисе; у целевого пользователя привязан `telegram_chat_id`.
- **Основной сценарий:**
  - *Событие «Новая сдача» (для преподавателя):*
    Бот отправляет сообщение:  
    `📥 Новая сдача работы!`  
    `Студент: Иванов Иван (ВПР42)`  
    `Работа: ЛР №2 «Архитектура REST API»`  
    `Дата сдачи: 28.10.2026 14:35`
  - *Событие «Смена статуса / Замечания» (для студента):*  
    `📋 Изменение статуса лабораторной работы!`  
    `Работа: ЛР №1 «Основы Git»`  
    `Новый статус: ⚠️ На доработке`  
    `Комментарий преподавателя: Добавьте описание команды git rebase.`
  - *Событие «Работа принята» (для студента):*  
    `🎉 Поздравляем! Ваша работа принята.`  
    `Работа: ЛР №1 «Основы Git»`  
    `Статус: ✅ Принята`
- **Исключения:**
  - *Telegram Bot API временно недоступен или вернул 429 Too Many Requests:* Сервис помещает сообщение в очередь с экспоненциальной задержкой (retry logic, до 3 попыток) без падения основного бэкенда.
  - *Пользователь заблокировал бота:* Ошибка логируется, флаг доставки сбрасывается.
- **Постусловие:** Сообщение доставлено пользователю в мессенджер.
