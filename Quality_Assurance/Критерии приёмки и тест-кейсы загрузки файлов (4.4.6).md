## 1. Цель работ

Совместно с аналитиком зафиксировать критерии приёмки файлового модуля и подготовить исполнимый набор проверок для:

- загрузки отчётов в форматах PDF, DOCX, ZIP через выбор файла и drag-and-drop;
- двухуровневой валидации: расширение, MIME-тип, сигнатура (magic bytes), структура DOCX, корректность ZIP, размер 0…20 МБ;
- автоматического перехода сдачи в `submitted`, фиксации `submitted_at`, SHA-256 и метаданных файла;
- повторной сдачи после `needs_work` с сохранением предыдущей версии;
- скачивания через приватный бакет MinIO и pre-signed URL с TTL 15 минут;
- прав доступа: 401 без токена, 403 на чужую сдачу и на загрузку преподавателем, защита от IDOR и прямого доступа к бакету;
- целостности: побитовое совпадение файла, откат при сбое MinIO или БД, отсутствие «осиротевших» объектов;
- комментариев и вердиктов: обязательный комментарий при «На доработке», видимость замечаний студенту, запрет комментирования студентом.

Тест-кейсы написаны как приёмочный контракт до реализации 4.4.2–4.4.5. Прогон выполняется в задаче 4.4.7 после появления MinIO, API и UI.

```powershell
# 20 МБ ровно: валидный PDF + добивка нулями до точного размера
$pdf = [IO.File]::ReadAllBytes("report_valid.pdf")
$size = 20971520
$buf = New-Object byte[] $size
[Array]::Copy($pdf, $buf, $pdf.Length)
[IO.File]::WriteAllBytes("report_20mb.pdf", $buf)
# 20 МБ + 1 байт
$buf2 = New-Object byte[] 20971521
[Array]::Copy($pdf, $buf2, $pdf.Length)
[IO.File]::WriteAllBytes("report_20mb_plus1.pdf", $buf2)
# Контрольная сумма
Get-FileHash .\report_valid.pdf -Algorithm SHA256
```

## 5. Критерии приёмки модуля

Критерии сформулированы совместно QA и аналитиком. Каждый критерий проверяется минимум одним тест-кейсом; для негативных границ указаны отдельные кейсы.

### 5.1. Функциональные критерии

| ID | Критерий | Способ проверки | ТК |
|---|---|---|---|
| F-01 | Студент загружает валидный PDF через выбор файла; файл попадает в приватный бакет, вычисляется SHA-256, статус становится `submitted`, `submitted_at` заполнен | `POST .../upload`, `mc ls`, `psql` | TC-FILE-001 |
| F-02 | Загрузка доступна через drag-and-drop и даёт тот же результат, что выбор через проводник | UI | TC-FILE-009 |
| F-03 | Поддерживаются DOCX с корректной OOXML-структурой и ZIP с корректным заголовком | `POST .../upload`, распаковка/проверка | TC-FILE-007, 008 |
| F-04 | Ключ объекта соответствует `submissions/{lab_id}/{student_id}/{UTC}_{short_uuid}_{sanitized_name}` и уникален | `mc ls`, БД | TC-FILE-012 |
| F-05 | Оригинальное имя сохраняется в `file_name` и возвращается при скачивании без искажений | `psql`, `Content-Disposition` | TC-FILE-012, TC-GRADE-003 |
| F-06 | Загрузка из `not_started` и `in_progress` переводит сдачу в `submitted` без ручного шага | API, БД | TC-FILE-010, 011 |
| F-07 | Повторная загрузка из `needs_work` создаёт новую версию, сохраняет предыдущую и возвращает `submitted` | API, `mc ls`, БД | TC-FILE-005 |
| F-08 | В статусах `submitted` и `accepted` форма загрузки заблокирована в UI, а прямой API-вызов даёт `409` | UI + `curl` | TC-FILE-040, 041 |
| F-09 | Преподаватель видит новую сдачу в ведомости с индикатором «Требует проверки» | UI, `GET /submissions` | TC-GRADE-004 |
| F-10 | `GET .../download-url` возвращает pre-signed URL, `expires_in_seconds=900`, файл скачивается как вложение | API, браузер | TC-GRADE-003, TC-FILE-042–044 |
| F-11 | Студент скачивает только свой файл, преподаватель — файл любого студента группы | API, RBAC | TC-FILE-042–044 |
| F-12 | Преподаватель добавляет комментарий ≥ 5 символов; при `needs_work` комментарий обязателен; студент видит замечания | API, UI | TC-GRADE-001, 002, 006, 008 |

### 5.2. Критерии валидации

| ID | Критерий | Способ проверки | ТК |
|---|---|---|---|
| V-01 | Разрешены только `.pdf`, `.docx`, `.zip`; остальные расширения отклоняются `400 INVALID_FILE_TYPE` | `curl`, UI | TC-FILE-017–020 |
| V-02 | MIME-тип проверяется и должен соответствовать формату; `text/plain` для `.pdf` отклоняется | `curl -F` | TC-FILE-034 |

| V-05 | ZIP проверяется через `zipfile.is_zipfile`; повреждённый и пустой архив отклоняются | Подмена файла | TC-FILE-027, 028 |
| V-06 | Файл 0 байт отклоняется `400 EMPTY_FILE`; форма не отправляет запрос | UI + API | TC-FILE-013 |
| V-07 | Ровно `20 971 520` байт принимается; `20 971 521` и более отклоняются `400/413 FILE_TOO_LARGE` | Граничные файлы | TC-FILE-002, 003, 015 |
| V-08 | Проверка размера выполняется и на клиенте, и на сервере; обход UI не позволяет загрузить большой файл | `curl` в обход UI | TC-FILE-003, 016 |
| V-09 | Двойное расширение, подмена расширения, path traversal, null-байт и слишком длинное имя не приводят к загрузке опасного файла или выходу за пределы префикса | Специальные файлы | TC-FILE-022, 023, 030–032 |
| V-10 | Nginx пропускает тело до 20 МБ + multipart-заголовки, то есть `client_max_body_size` не меньше `21m` | Статическая проверка `nginx.conf` + загрузка 20 МБ | TC-FILE-035 |
| V-11 | Сервер читает и валидирует файл инкрементально и не буферизирует гигантский поток в память | Код-ревью + загрузка 20 МБ, контроль памяти контейнера | TC-FILE-036 |

### 5.4. Критерии целостности и отказоустойчивости

| ID | Критерий | Способ проверки | ТК |
|---|---|---|---|
| I-01 | SHA-256, сохранённый при загрузке, совпадает с хешем скачанного файла | `Get-FileHash`, `psql` | TC-FILE-051, TC-GRADE-003 |
| I-02 | При сбое `put_object` в MinIO статус и предыдущая версия не меняются, пользователь получает `500 STORAGE_ERROR` | Отключение MinIO | TC-FILE-006 |
| I-03 | При сбое записи в БД после успешной загрузки выполняется компенсирующее удаление объекта | Эмуляция сбоя БД, `mc ls` | TC-FILE-054, 055 |
| I-04 | После неудачной загрузки не остаётся «осиротевших» объектов и частичных записей | `mc ls`, `psql` | TC-FILE-055 |

- известные замечания из раздела 8 учтены при разборе результатов.

**Критерии выхода:**

- все критерии F-01…F-12, V-01…V-11, S-01…S-10, I-01…I-08, C-01…C-06 подтверждены или оформлены дефектами;

- сбои MinIO и БД не оставляют частичных данных;

## 11. Выводы

Совместно с аналитиком подготовлены 47 критериев приёмки (функциональные, валидация, права и безопасность, целостность, комментарии) и 79 тест-кейсов `TC-FILE-001…061`, `TC-GRADE-001…018`. Покрыты загрузка PDF/DOCX/ZIP, drag-and-drop, границы 0 байт и 20 МБ, magic bytes, подмена расширения, path traversal, права и IDOR, pre-signed URL и TTL, версионность, SHA-256, сбои MinIO и БД, а также комментарии и вердикты.

На текущей сборке выполним только 1 кейс статически — проверка `client_max_body_size` в Nginx. Остальные 78 кейсов заблокированы до реализации 4.4.2 (MinIO, таблицы файлов и версий), 4.4.3 (API), 4.4.4–4.4.5 (UI) и 4.4.8 (синхронизация контрактов). Это ожидаемо: критерии и тест-кейсы подготовлены как приёмочный контракт до разработки модуля и будут прогнаны в 4.4.7.

Ключевые риски: отсутствие MinIO и файловых полей в модели; лимит Nginx `1m`, который заблокирует почти все реальные отчёты; отсутствие серверной проверки magic bytes и структуры DOCX; неверный Host при подписи pre-signed URL; отсутствие версионности и компенсирующего удаления. Без устранения этих пунктов модуль нельзя считать готовым даже при работающем UI-сценарии.
