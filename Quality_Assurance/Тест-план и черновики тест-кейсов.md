# Отчёт по задаче 5.1.1 — Тест-план и черновики тест-кейсов

**Задача ИСР:** 5.1.1. [QA] Составление тест-плана и черновиков тест-кейсов по ключевым сценариям на вехе «Проектирование завершено»

**Период выполнения:** 4–5 ноября 2026 г.
**Статус:** Выполнено
**Связанные документы:** [[Use Cases]], [[User Stories]], [[Definition of Done]], [[Спецификация API (OpenAPI)]], [[Схема базы данных (ERD)]], [[Матрица ролей и прав доступа]]

## 1. Цель работ

Сформировать тест-план MVP LabFlow и подготовить черновики тест-кейсов по ключевым сценариям, чтобы на вехе «Проектирование завершено» была готова основа для функционального, интеграционного и регрессионного тестирования.

### 2.2. Границы тестирования (MVP)

**Входит в объём:**

- аутентификация и авторизация, роли «Студент» / «Преподаватель»;
- CRUD лабораторных работ и дедлайнов;
- список работ, фильтры и отображение дедлайнов;
- жизненный цикл статусов: `Не начата` → `В работе` → `Сдана` → `На доработке` → `Принята`;
- загрузка отчётов и рецензирование;
- ведомость группы и скачивание файлов;
- привязка Telegram и уведомления;
- негативные сценарии: 401, 403, 500 с откатом, запрещённые переходы статусов, лимит 20 МБ, блокировка «На доработку» без комментария.

**Не входит в объём (Out of Scope MVP):**

- командная сдача работ;
- CI runner и интеграция с внешними системами (деканат, Moodle);
- чат в реальном времени;
- нагрузочное тестирование и проверка HA/отказоустойчивости инфраструктуры.

## 3. Стратегия тестирования

| Уровень | Что проверяется | Способ | Когда |
|---|---|---|---|
| Smoke | Доступность окружения и ключевых точек входа | Ручной чек-лист | Перед каждым прогоном (5.1.2) |
| Функциональное (UI) | Сценарии пользователей по US/UC | Ручное тестирование в браузере | По модулям, после сборки |
| API / контрактное | Эндпоинты, коды ответов, схемы ошибок | Postman / curl, сверка с OpenAPI | Параллельно с UI |
| Интеграционное | PostgreSQL, файловое хранилище, Telegram | Проверка связки компонентов, мок внешнего API | После стабилизации модуля |
| Негативное и граничное | Некорректные данные, права, лимиты | Ручные и API-проверки | В каждом модуле |
| Регрессионное | Отсутствие поломок смежных модулей | Смоук-набор + регресс по трассировке | На каждой вехе |
| Приёмочное | Соответствие AC и DoD | Чек-лист приёмки, прогон Must Have | Перед закрытием вехи |

**Приоритизация:** сначала Must Have (FR-01…FR-08), затем Should/Could (FR-09, FR-10). Критичные дефекты (Blocker/Critical) блокируют веху.

**Тестовые данные:** одна академическая группа ВПР42, пользователи с ролями «Студент» и «Преподаватель», работы во всех пяти статусах, файлы в пределах лимита и на границе 20 МБ, даты дедлайна (3 дня / 0 / −1).

## 6. Критерии входа и выхода

**Критерии входа:**

- окружение поднято, smoke-тесты пройдены;
- требования (US, UC, AC) и DoD зафиксированы;
- сборка доступна для тестирования;
- тестовые данные подготовлены.

**Критерии выхода (веха «Проектирование завершено»):**

- для каждого AC есть минимум 1 позитивный и 1 негативный тест-кейс (S3);
- все Must Have истории пройдены на тестовом окружении (S4);
- нет открытых дефектов Blocker/Critical по Must Have;
- баг-репорты оформлены по шаблону (S6);
- отчёт о приёмке подписан QA + PO (S7).

## 7. Управление дефектами

| Severity | Описание | Реакция |
|---|---|---|
| Blocker | Окружение не работает, ключевой сценарий полностью недоступен | Блокирует веху, исправление немедленно |
| Critical | Потеря данных, обход прав, невозможность сдать/принять работу | Блокирует веху |
| Major | Сценарий работает с существенным отклонением, есть обходной путь | Исправить до вехи |
| Minor | Косметические ошибки, неудобства без влияния на сценарий | Допускается перенос |

Баг-репорт содержит: заголовок, окружение, шаги воспроизведения, ожидаемый и фактический результат, severity, вложения, связанный US/UC/AC.

## 8. Риски

| Риск | Влияние | Митигация |
|---|---|---|
| MinIO отсутствует в текущем `docker-compose.yml` | Нельзя проверить загрузку/скачивание файлов в полном контуре | Приоритетно добавить сервис; до этого проверять файловые сценарии на моках с фиксацией ограничения |
| Нет миграций (используется `create_all`) | Расхождение схемы между средами | Зафиксировать как технический долг, проверять схему перед прогоном |
| Telegram API недоступен/нестабилен | Ложные падения тестов уведомлений | Использовать мок и журнал событий, отдельно проверять retry/429 |
| Сжатые сроки вехи | Неполное покрытие | Приоритет Must Have, покрытие Should/Could — после |
